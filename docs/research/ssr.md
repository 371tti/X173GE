# Screen-space reflections (SSR)

## Source and scope

Morgan McGuire and Michael Mara, “Efficient GPU Screen-Space Ray Tracing,” Journal of Computer Graphics Techniques 3(4), 2014. [Paper and supplemental implementation](https://jcgt.org/published/0003/04/04/)

## Chosen first variant

Use the paper’s perspective-correct 2D DDA traversal over one camera depth layer. Project the reflected camera-space ray to screen coordinates and advance through adjacent pixels (including diagonal neighbors), sampling each at most once. `P` is the screen-space DDA position; `Q = cameraPosition / clipW` and `k = 1 / clipW` are the perspective-correct quantities interpolated along it. Recover the camera-space point as `Q / k`. The paper's one-layer path does not need its multiple-depth-layer loop. Clip the ray to the viewport and explicitly handle single-pixel, zero-length, and quadrant-flipped paths. This is thin-line traversal, not a conservative/supercover traversal of every crossed pixel.

A hit tests the containing depth texel, then bilinearly samples HDR scene color at the DDA's subpixel position. This smooths color lookup without changing the intersection test; neighboring colors can still bleed across depth edges. The paper's `zThickness` is an interval along camera-space z, not a distance along the ray. A user-facing world-unit setting must be converted to the view-depth interval and documented as such. A miss or off-screen ray keeps the full base PBR result and contributes no reflection. There is no environment-map or analytic sky/ground specular fallback. A hit adds reflected scene color, weighted by Fresnel, SSR intensity, and edge fade; direct and diffuse lighting remain in the base PBR result. SSR cannot reveal geometry outside the current view. Roughness limits and fades are composition extensions around the ray marcher, not proof that it finds the physical reflected surface. This subpixel lookup is not roughness filtering.

## Assumptions and deliberate omissions

The method sees only the camera depth/color buffers. It cannot reflect off-screen objects, hidden depth layers, or disoccluded surfaces. A single depth layer causes missed or false intersections at thin geometry and depth discontinuities. Screen-space reflection is therefore a partial reflection source, not world-space ray tracing. Multiple depth layers are a research-supported extension but add buffers and complexity; defer them until the validation scene demonstrates a real need.

Input requirements: linear HDR color, depth with a documented projection convention, normal, roughness, and per-pixel reflectance for material-weighted composition. The current G-buffer normal is world-space, so use the inverse view-projection reconstruction and the camera's world forward vector consistently, or add and validate a view transform. Current/previous transforms are needed only if temporal stabilization is added later. The reflection pass must consume depth after the depth-producing scene pass and run before tone mapping. It must read one color image and write another; sampling from the same color attachment being rendered is not valid. Blended items do not write the depth/normal G-buffer and must not be treated as opaque SSR surfaces.

## Visual validation

Use a metallic floor with a roughness gradient, thin rails in front of a second surface, and a moving object crossing the reflection. Include a bright reflected object that exits the screen, camera motion over a grazing reflection, and a depth edge. Inspect hit popping, thickness leaks, edge fade, roughness response, and whether misses leave the existing PBR result without stale data. First validate a fixed-camera scene with one clearly identifiable emissive object reflected by a low-roughness floor; vary roughness and move the object off-screen only after hit placement is correct.

## Paper details checked before implementation

- Source: Morgan McGuire and Michael Mara, “Efficient GPU Screen-Space Ray Tracing,” *Journal of Computer Graphics Techniques* 3(4), 2014, §§2–4 and Listings 2–4. The paper uses right-handed camera space with +z out of the screen and negative object z; near-plane clipping uses `nearPlaneZ = -near`.
- For a ray point `X`, projection `M`, and homogeneous point `H = M * vec4(X, 1)`, use `k = 1 / H.w`, `Q = X * k`, and projected pixel `P`. `Q` and `k` vary linearly along the 2D line; recover `X = Q / k`. The DDA permutes axes when `abs(delta.x) < abs(delta.y)` and uses `stepDir = sign(delta.x)`, `invDx = stepDir / delta.x`, `dP = (stepDir, delta.y * invDx)`, `dQ = (Q1 - Q0) * invDx`, and `dk = (k1 - k0) * invDx`.
- With X173GE's Vulkan clip coordinates and positive-height viewport, convert NDC to top-left pixel coordinates with `P = ((H.x / H.w * 0.5 + 0.5) * width, (0.5 - H.y / H.w * 0.5) * height)`. The shader uses `gl_FragCoord` and `texelFetch` with that same framebuffer convention.
- At each step compare the ray's z interval `[rayZMin, rayZMax]` with the one-layer surface interval `[sceneZ - zThickness, sceneZ]`. The camera depth attachment uses reverse-Z and clears to `0.0`; its values are nonlinear and cannot be compared directly to camera-space z. X173GE reconstructs positions from the inverse view-projection matrix. Explicit viewport bounds checks are required before `texelFetch`; clamping out-of-range coordinates would create edge hits.
- The first implementation uses stride 1 and no jitter, one depth layer, and no temporal history. A screen-space hit adds screen color to the base PBR result using Fresnel, the configured intensity, and edge fade; misses preserve the base PBR color with no reflection fallback. The paper's thin-line DDA visits adjacent pixels but is not conservative. Its max distance, step count, thickness, and composition weight must be selected and reported with visual and GPU-time measurements rather than claimed as universally correct constants.
- The hit color uses the subpixel DDA location for linear filtering. The paper identifies subpixel hit refinement with bilinear color sampling as a way to smooth indirect-light results; X173GE keeps its original containing-texel depth test, so this improves color sampling but does not repair false depth intersections or implement rough-surface cone filtering.
- X173GE exposes `max_distance`, `thickness`, `max_steps`, `max_roughness`, `intensity`, and `edge_fade_pixels` in `SsrSettings`. Its current demo preset is 15 world units, 0.1 view-depth units, 192 pixels, 0.85 roughness, unit intensity, and a 16-pixel viewport fade. These are scene-tuned values for visual and GPU-time calibration, not values claimed by the paper.
- The first implementation renders opaque objects into the trace color/depth buffers, resolves SSR into a distinct HDR image, then draws sorted blended objects over that result with depth testing and depth writes disabled. This keeps blended colors from being paired with opaque depth during ray hits. The optional linear RGBA8 F0/F90 attachment is allocated only when SSR is requested.
